# Marcas, colores de filamento y archivo

En **Configuración → Marcas**, usa «Nueva marca» o selecciona «Marca guardada» y pulsa «Editar marca». Escribe el nombre, elige el color representativo y pulsa «Guardar marca»; seleccionar o cambiar un campo no guarda nada. Renombrar o recolorear conserva el ID y los nombres anteriores como alias de esa cuenta. En **Configuración → Bobinas**, elige «Marca de la bobina» por identidad. Al editar una bobina, «Color del filamento» es un único campo de solo lectura que reúne el nombre registrado y su muestra automática. No hay casilla para activar muestras ni selector manual de HEX. Sin muestra guardada, Configuración y Consultar bobinas pueden mostrar una aproximación nominal de colores básicos, siempre rotulada «Aprox.»; los nombres especiales conservan su texto y muestran «Sin muestra». Guardar la bobina es una acción separada.

Configuración muestra primero la muestra del **filamento** (cuadrada), su nombre y «Aprox.» cuando corresponde; el indicador redondo de marca permanece separado. Consultar bobinas tiene una columna propia «Color del filamento», con etiqueta por fila en móvil. La Calculadora conserva su selector anterior: marca primero y muestra de filamento solo si hay un HEX guardado. Una marca heredada sin color configurado muestra un indicador neutro. Primero se busca el ID de marca asociado; para perfiles heredados sin asociación y compras se comparan alias normalizados dentro de la cuenta. Consultar las listas no escribe perfiles, compras ni cotizaciones. Los importes y textos históricos guardados no cambian con los nombres actuales. Un conflicto de revisión pide recargar antes de guardar otra vez.

## Paleta actual del catálogo

El 29 de octubre de 2026 se asignaron **10 colores diferentes a las 10 marcas existentes** de la cuenta del catálogo. Son identificadores visuales de la aplicación, no una declaración de colores oficiales de los fabricantes. La comprobación posterior confirmó que no se repiten y conservó nombres, IDs, alias, bobinas, precios y registros históricos. El color de marca sigue siendo independiente del nombre y de la muestra del filamento.

## Contrato técnico

A brand is an owner-scoped identity with a stable UUID, editable name and representative color. T2 relates profiles to that identity and adds independent filament names and optional samples. Purchases, quotes and counters retain their original snapshots.

## Public path

1. Apply `202610230001_calc3d_brands.sql` **after** the spool-profile migration, as the migration owner (not through the app). Existing nonempty brand text from profiles and purchased spools creates one brand per owner and normalized key, with `color: null` until the owner chooses a color.
2. On an admitted authenticated session, use `createRemoteRepositories(client, session).brands.list()`; entries are detached DTOs. For a brand name lookup, normalize legacy text with `normalizeBrandName(text)` and find that key in the brand's `aliases` array. Never compare another owner's list.
3. Save with `brands.createBrand({ name, color })` or `brands.updateBrand(id, { name, color }, expectedRevision)`. A save returns `{ ok: true, brand: DTO }`. Conflicts require reloading, not automatic retry.
4. Apply `202610230002_calc3d_profile_brand_colors.sql` after T1 as the migration owner. The profile list returns `brandId`, `filamentColor` and `filamentColorHex` alongside the original fields. Existing profile IDs, price, weight, revision and timestamps do not change during the association backfill. The T3 UI reads this registry and projects display copies; no automatic brand creation or hash-color fallback is used.

## Shapes and normalization

| Surface | Exact shape |
| --- | --- |
| Input | `{ name: string, color: '#RRGGBB' }`; name trimmed and internal whitespace collapsed; color uppercase on save. Color required for new/edited records. |
| DTO | `{ id, name, normalizedName, color, aliases, revision, createdAt, updatedAt }`; `color` is null only for unconfigured legacy records, `aliases` is an array of normalized string keys. |
| REST list | `calc3d_brands` SELECT `id,name,normalized_name,color,aliases,revision,created_at,updated_at` (admitted owner only). |
| RPC | `calc3d_save_brand(payload jsonb, brand_id uuid default null, expected_revision bigint default 0)` returns a brand row. Create uses null ID and revision 0; update requires its ID and current positive revision. |

New/edited names reject Unicode general categories **Cc** (controls) and **Cf** (format characters), matching `validateBrand` (including zero-width characters such as U+200B); a PostgreSQL `C`-collation code-point range check enforces the same exclusion in the RPC and for configured-color rows. Ordinary accented names and emoji remain valid. Name identity is lowercased, trimmed and whitespace runs collapsed **within the owner**. It does not correct spelling. On rename the old key stays in `aliases`, so legacy purchase text can still identify the same brand without rewriting a snapshot. A former alias cannot be assigned to another brand of that owner. Different owners can use identical names. Legacy purchased labels longer than 120 characters remain readable, but an edited name must fit the new 120-character limit. If existing profile/purchase brand text contains Cc/Cf, the additive migration refuses transactionally (`23514`, `Legacy brand name contains unsupported control or format characters`); it does not strip text, merge names, or rewrite any historical row. Preflight and resolve such incompatible source data with the migration owner before applying; no live migration is part of T1. No physical delete, merge or restore API exists.

## Profile relation and independent filament color (T2)

| Surface | Exact contract |
| --- | --- |
| Profile DTO | Existing fields plus `brandId: UUID \| null`, `filamentColor: string`, `filamentColorHex: '#RRGGBB' \| null`. The readable name can be empty for unknown legacy filament. Empty names have no sample. |
| REST list | `calc3d_spool_profiles` SELECT additionally `brand_id,filament_color,filament_color_hex`; these map to the camelcase DTO names above. Old response mocks without optional columns map to null / empty / null; present invalid columns fail parsing. |
| RPC | The **same** `calc3d_save_spool_profile(payload jsonb, profile_id uuid default null, expected_revision bigint default 0)` accepts optional camelcase `brandId`, `filamentColor`, `filamentColorHex` in `payload`, in addition to existing fields. |
| Color input | Trimmed readable name, at most 120 code points, no Unicode Cc/Cf; optional six-digit hex uppercased on save. Supply `filamentColor` with any nonnull `filamentColorHex`. A named color may intentionally have null/no sample. |

Missing `brandId`, `brand`, `filamentColor` and `filamentColorHex` keys on **updates** retain their stored values. The domain validator and repository pass presence through rather than inserting defaults. Explicit `brandId: null` clears association; without a supplied `brand` it also clears the old brand label, while an explicit label stays readable but unassociated. Explicit `filamentColor: ''` clears the name and its sample; `filamentColorHex: null` clears only the sample. On creation, omitted fields default to unassociated, empty brand/color names and null sample. A `brandId` selection requires an owner-owned registry row; its **current registry name** is stored as the compatible profile `brand` text regardless of an additional supplied brand label. Text-only saves resolve owner aliases (including previous names); unknown strings remain readable and unassociated. Association never changes historical purchase/quote text, and renaming a registry brand does not rewrite existing profile text. T3 resolves the current registry name/color in lists.

The database enforces `(owner_id,brand_id)` via composite FK in addition to RPC owner lookup. Invalid payloads and missing/foreign brand IDs return `23514`, `Invalid spool profile`; stale/foreign profile revision returns `40001`, `Spool profile revision conflict`; denied admission returns `28000`, `Calc3D access denied`. Rejection leaves business rows/counters untouched. Only the RPC may mutate authenticated profiles; explicit save acknowledgement remains `{ ok: true, profile: DTO }` after a verified response.

## Failure contract

The RPC rejects invalid payload/revision with SQLSTATE `23514`, `Invalid brand`; occupied names (including prior aliases) with `23505`, `Brand name already in use`; missing, foreign or stale update with `40001`, `Brand revision conflict`; absent or disabled admission with `28000`, `Calc3D access denied`. It is atomic: no brand/alias update survives a rejection. The repository validates before RPC, maps revision conflicts to `La marca cambió; recarga antes de guardar.`, and fences owner/access both before and after every read/write. Direct authenticated table mutation and anonymous table/RPC access are not granted.

## Archivo de catálogo

La eliminación solicitada significa **archivo**, no borrado: solo marca y perfil de bobina de Configuración. La migración aditiva `202610230003_calc3d_catalog_archive.sql` se aplica después de `202610230002_calc3d_profile_brand_colors.sql` por el responsable de migraciones; nunca desde la página. Agrega `archived_at timestamptz` nullable a ambas tablas. El DTO conserva todas sus propiedades anteriores y agrega `archivedAt: string | null`; las listas owner-scoped siguen devolviendo **también** registros archivados para resolver relaciones e historial. Configuración ofrece «Quitar marca» y «Quitar bobina» para registros guardados, con confirmación cancelable que explica que desaparecen de las listas sin perder el historial. No se puede quitar un registro nuevo sin guardar. El cotizador muestra solo perfiles activos y compras; una marca archivada conserva su nombre y color para representar por ID los perfiles aún activos, pero no figura como opción nueva de marca. Una bobina ya asociada conserva su referencia al editarla, sin restablecer ni borrar silenciosamente su marca. Archivar una marca **no** archiva automáticamente sus perfiles; las compras y cotizaciones históricas, precios y pesos, alias y contadores permanecen intactos. No hay restauración ni reutilización automática de identidad.

`brands.archiveBrand(id, expectedRevision)` llama `calc3d_archive_brand(brand_id uuid, expected_revision bigint)`; `spoolProfiles.archiveProfile(id, expectedRevision)` llama `calc3d_archive_spool_profile(profile_id uuid, expected_revision bigint)`. Cada éxito devuelve `{ ok: true, brand: DTO }` o `{ ok: true, profile: DTO }`, con `archivedAt` no nulo y revisión incrementada. Ambos RPC validan ingreso admitido (`28000`, `Calc3D access denied`), ID/revisión nula o fuera de rango (`23514`, `Invalid brand archive` / `Invalid spool profile archive`), y propiedad/revisión CAS o repetición de archivo (`40001`, `Brand revision conflict` / `Spool profile revision conflict`). El repositorio traduce los conflictos a los mensajes de recarga preexistentes y comprueba el dueño antes y después de la escritura. No concede DML directo ni acceso anónimo. Los RPC de guardado existentes no modifican `archived_at`, incluso al recibir payloads anteriores; no introducen un mecanismo de restauración.

El archivo es irreversible desde la interfaz: no hay función de restauración ni borrado físico. Una respuesta remota diferida de una cuenta anterior no debe repoblar la vista de la cuenta actual. La verificación de navegador de estos controles sigue pendiente.

## Muestra visual del filamento

El HEX personalizado guardado tiene prioridad sobre el nombre, aunque ambos difieran. Si falta, la representación de Configuración y Consulta reconoce únicamente nombres básicos completos (sin distinguir mayúsculas ni acentos): Blanco, Negro, Rojo, Verde, Azul, Amarillo, Naranja, Morado, Violeta, Rosa, Gris, Marrón, Café y Beige. Sus muestras son aproximaciones nominales, no tonos certificados del fabricante. No se infiere un tono desde el nombre del producto, la marca, fragmentos de texto, mezclas, acabados, transparencias ni nombres especiales.

El nombre siempre permanece visible. Las aproximaciones llevan «Aprox.» y los demás nombres sin HEX muestran «Sin muestra», nunca un gris presentado como si fuera su color. El campo de color es informativo: no permite escribir el nombre ni elegir una muestra. Consultar, seleccionar o editar una bobina no guarda ningún dato. Al guardar explícitamente el precio o el peso se conservan el nombre y el HEX ya registrados, sin convertir una aproximación en una muestra almacenada. Las bobinas nuevas sin datos de color muestran «Sin color indicado» y «Sin muestra»; no se deduce un tono desde el nombre comercial. Precios, pesos, identidades e historial no se deducen ni reescriben. El cambio de cuenta limpia también las muestras y previews.
